# Device simulator — design

**Date:** 2026-04-24
**Location:** `apps/simulator/` (new top-level `apps/` directory)
**Slice scope:** first non-Terraform slice. One local Python app.

## Purpose

Close the loop on the ingest path built over the past three slices (LAW → Event Grid → Event Hubs → IoT Hub). The simulator is a local Python process that authenticates to IoT Hub as a SAS-provisioned device (`sim-01`) and continuously pushes realistic-looking device telemetry and occasional crash-suspect events. Running it should produce visible, measurable activity in the Event Hub, the IoT Hub metrics, and App Insights custom events — proving the infrastructure works, not just plans.

## Context

Current stack (commit `92eac54`): subscription + RG + budget + Log Analytics + App Insights + Event Grid lifecycle topic + Event Hubs namespace + `telemetry` hub + IoT Hub with identity-based route to that hub. IoT Hub has SAS device auth enabled specifically so this simulator can connect without an X.509 story.

Architecture commits (`docs/architecture.md`):
- Python for Functions and simulator.
- Simulator uses SAS device auth; real devices would use X.509.
- All device messages route to the `telemetry` Event Hub; downstream classifier discriminates crash-suspects on message properties, not at ingest (decision #7).

## Project layout

New top-level `apps/` directory anticipating future Python components (telemetry-writer, classifier, notifier, user-api, ml-stub).

```
apps/simulator/
  bootstrap.py           # registers sim-01 device, writes .env
  simulator.py           # entry point; reads .env, runs async send loops
  payload.py             # pure functions that build telemetry / crash dicts
  tests/
    __init__.py
    test_payload.py      # unit tests (pytest)
  requirements.txt       # runtime deps
  requirements-dev.txt   # pytest, ruff
  .env.example           # committed; template with placeholder values
  .gitignore             # ignores .env and .venv
  README.md              # bootstrap + run instructions
```

Why split `payload.py` out: it is the only portion with testable logic (value ranges, JSON shape, `eventType` tagging). Network code in `simulator.py` is thin glue; mocking the IoT SDK to "test" it adds no real signal. Keep the testable surface honest.

## Components

### `bootstrap.py`

Responsibility: make sure the `sim-01` device exists in IoT Hub's identity registry and persist its connection string + related config into `.env`.

Behavior:
- Fetch the IoT Hub `iothubowner`-policy connection string by shelling out to `az iot hub connection-string show --hub-name iot-guardianlink-dev-weu --policy-name iothubowner --query connectionString -o tsv`. This leverages the user's existing `az login` without requiring a separate Entra data-plane role grant (IoT Hub RBAC is not inherited from subscription Owner; using SAS here sidesteps the permission question entirely).
- Use `azure-iot-hub` SDK's `IoTHubRegistryManager.from_connection_string(owner_conn)` to:
  1. Look up device `sim-01` by ID.
  2. If it doesn't exist, create it with SAS authentication (primary/secondary keys auto-generated by IoT Hub).
  3. Fetch the primary connection string (`HostName=...;DeviceId=sim-01;SharedAccessKey=...`).
- Fetch the App Insights connection string the same way: `az monitor app-insights component show -g rg-guardianlink-dev --app appi-guardianlink-dev-weu --query connectionString -o tsv`. (Direct `az` is simpler than the `azure-mgmt-applicationinsights` SDK for this one read.)
- Write `.env` with:
  ```
  IOTHUB_DEVICE_CONNECTION_STRING=...
  APPLICATIONINSIGHTS_CONNECTION_STRING=...
  TELEMETRY_PERIOD_S=20
  CRASH_PERIOD_S=120
  DEVICE_ID=sim-01
  ```
- Idempotent: re-running on an existing device re-fetches the connection string and rewrites `.env`. Safe after a `terraform destroy`/apply cycle that recreates the IoT Hub (the device identity is data-plane state and vanishes with the hub).

Hardcoded values (no CLI args, no env-var indirection — only one instance of each in the dev stack):
- `IOTHUB_NAME = "iot-guardianlink-dev-weu"`
- `RESOURCE_GROUP = "rg-guardianlink-dev"`
- `APPINSIGHTS_NAME = "appi-guardianlink-dev-weu"`
- `SUBSCRIPTION_ID = "WORKLOAD_SUBSCRIPTION_ID_PLACEHOLDER"`
- `DEVICE_ID = "sim-01"`

If the user later adds more devices / runs in a different subscription, these promote to CLI flags. YAGNI for now.

### `simulator.py`

Responsibility: connect as `sim-01` and push telemetry + crash-suspect events until Ctrl-C.

Behavior:
- Load `.env` via `python-dotenv`.
- Configure `azure-monitor-opentelemetry` with `APPLICATIONINSIGHTS_CONNECTION_STRING`.
- Instantiate `IoTHubDeviceClient.create_from_connection_string(...)`. Use the async variant (`azure.iot.device.aio`).
- Connect; log connection state to stdout + emit `connection_restored` custom event on first connect.
- Run two asyncio tasks concurrently:
  - **Telemetry loop**: every `TELEMETRY_PERIOD_S` seconds, build `payload.build_telemetry(device_id, datetime.now(timezone.utc))`, wrap in `azure.iot.device.Message`, set `message.custom_properties["eventType"] = "telemetry"`, call `client.send_message(msg)`, emit `MessageSent` custom event with dimensions `{event_type: "telemetry", device_id}`.
  - **Crash loop**: every `CRASH_PERIOD_S` seconds, build `payload.build_crash_suspect(...)`, set `eventType = "crash_suspect"`, send, emit `MessageSent` with `event_type: "crash_suspect"`.
- On connection-state change events from the SDK, emit `connection_lost` / `connection_restored` custom events.
- Ctrl-C (SIGINT): cancel tasks, `await client.shutdown()`, exit 0.

Rate math: defaults (`TELEMETRY_PERIOD_S=20`, `CRASH_PERIOD_S=120`) produce 4320 telemetry + 720 crash = **5040 msgs/day**. F1 IoT Hub cap is 8000/day; this leaves 37% margin for a 24h run. Faster rates burn the cap proportionally; warn in the README.

No retry / backoff logic written by hand. The `azure-iot-device` SDK auto-reconnects on transient failures.

### `payload.py`

Pure functions, no I/O, no globals. Testable.

```python
def build_telemetry(device_id: str, now: datetime) -> dict:
    """Plausible steady-state device reading."""

def build_crash_suspect(device_id: str, now: datetime) -> dict:
    """Device reading that trips the on-device crash heuristic."""
```

Output shape (both functions return the same keys; only value ranges differ):

```json
{
  "device_id": "sim-01",
  "timestamp": "2026-04-24T19:30:00.123456+00:00",
  "accelerometer": {"x": 0.12, "y": -0.05, "z": 0.98},
  "gps": {"lat": 52.3676, "lon": 4.9041},
  "battery_pct": 87.2,
  "heart_rate_bpm": 72,
  "suspect_confidence": null
}
```

Value ranges:

| Field | Telemetry | Crash-suspect |
|---|---|---|
| `accelerometer.{x,y,z}` | uniform ±1.5 g | at least one axis \|a\| ≥ 3.0 g (up to ±12 g) |
| `gps.lat` | 52.3676 + uniform ±0.0005 | same |
| `gps.lon` | 4.9041 + uniform ±0.0005 | same |
| `battery_pct` | uniform 20–100 | same |
| `heart_rate_bpm` | int 60–90 | int 120–180 |
| `suspect_confidence` | `None` | uniform 0.4–0.8 |

The GPS centre is Amsterdam-ish; no configurability — it's a simulator. Battery does not track state between calls (stateless simulator). HR is an int because bpm commonly is.

Crash discrimination lives in the **IoT Hub custom property** `eventType`, not in the body. All messages hit the same route and the same Event Hub per architecture decision #7. Downstream classifier will filter on the property.

### `tests/test_payload.py`

Unit tests, no network, no environment. Run under pytest.

- `test_telemetry_value_ranges` — 100 samples, assert all fields fall within the telemetry table above.
- `test_crash_suspect_has_confidence` — crash-suspect payload has `suspect_confidence` in [0.4, 0.8]; telemetry has it `None`.
- `test_crash_suspect_accelerometer_spikes` — crash-suspect has at least one axis with `|a| >= 3.0`.
- `test_heart_rate_ranges_disjoint` — 100 samples each: telemetry HR max ≤ 90; crash HR min ≥ 120.
- `test_timestamp_roundtrips` — the `timestamp` field parses back via `datetime.fromisoformat`.
- `test_required_keys_present` — both payloads contain all expected top-level keys.

No integration tests against IoT Hub. Adding them means provisioning a device in CI and paying for message traffic; out of scope.

## App Insights instrumentation

The simulator is the **first application component** in the stack; the project's observability-from-day-1 principle is meaningless if we exempt it. Worth the ~20 lines.

Approach:
- `logging.basicConfig(...)` runs FIRST (so stderr gets a StreamHandler), then `azure-monitor-opentelemetry.configure_azure_monitor()` attaches its handler. Reversed order means basicConfig sees existing root handlers and becomes a no-op — stderr goes silent.
- `configure_azure_monitor()` reads `APPLICATIONINSIGHTS_CONNECTION_STRING` and wires OpenTelemetry logs + traces + metrics to App Insights.
- Logged events emitted via the standard `logging` module with `extra={<key>: <value>, ...}` — each `extra` key becomes a direct `customDimensions.<key>` attribute in App Insights. Do NOT nest under a `custom_dimensions` sub-dict as the older `opencensus-ext-azure` SDK required: the OTel distro stores that as a single stringified attribute and `customDimensions.event_type` queries return empty.
- The OTel distro routes Python log records to the **`traces`** table in Application Insights (not `customEvents` — that table requires the older App Insights SDK's `track_event` API, which the OTel distro does not use).

Events (log records in the `traces` table, discoverable by message text + custom dimensions):
| Log message | Dimensions | When |
|---|---|---|
| `message_sent` | `event_type` (telemetry \| crash_suspect), `device_id` | Each successful `send_message` return |
| `message_send_failed` | `event_type`, `device_id`, `error` | On exception from `send_message` |
| `connection_restored` | `device_id` | On CONNECTED state from SDK |
| `connection_lost` | `device_id`, `reason` | On DISCONNECTED / ERROR from SDK |

Kusto query to validate (post-run):
```
traces
| where message == "message_sent"
| summarize count() by tostring(customDimensions.event_type), bin(timestamp, 1m)
```

## Verification after running ~2 minutes

1. **Portal → IoT Hub → Metrics → "Total number of messages used"** — should show ≥ 6 messages (6 telemetry + 1–2 crash).
2. **Portal → Event Hub `telemetry` → Process data / Data Explorer** — can view raw messages landing; confirm the `eventType` custom property.
3. **App Insights → Logs**:
   ```
   traces | where message == "message_sent"
     | summarize count() by tostring(customDimensions.event_type)
   ```
   Expect majority `telemetry`, a few `crash_suspect`.
4. **LAW:**
   ```
   AzureDiagnostics
   | where ResourceType == "IOTHUBS" and Category == "Connections"
   | project TimeGenerated, OperationName, Level
   | order by TimeGenerated desc
   | take 10
   ```
   Expect `deviceConnect` / `deviceDisconnect` rows for the simulator run. The `Routes` and `DeviceTelemetry` categories are intentionally **error-only** in IoT Hub diagnostics — they log route misconfig / message-pipeline failures, not successful deliveries. A healthy route produces zero rows there; that is the correct state, not a regression.

## Risks and notes

- **F1 quota silently 429s.** Defaults leave 37% margin but an aggressive reconfiguration of `TELEMETRY_PERIOD_S` can blow through 8000/day in a few hours. README warns.
- **`az login` required.** `bootstrap.py` uses `DefaultAzureCredential`; if `az account show` fails, bootstrap fails with a clear error.
- **Device registry resets on `terraform destroy`.** Bootstrap is idempotent and will re-create `sim-01` on the next run. This is expected rhythm.
- **Connection string in `.env`.** SAS device key; leaking it lets someone impersonate `sim-01` to the hub. `.env` is gitignored; `.env.example` has only placeholders. Production solutions (certificate-based auth) are a separate slice.
- **App Insights connection string is also in `.env`.** Lower sensitivity but still ingress-able. Same containment as above.
- **Simulator is stateless.** Battery doesn't decay; GPS doesn't drift realistically. Good enough for "prove the pipeline works"; not good enough for "train a classifier." When the classifier slice lands, consider adding realism (or switch to replayed real-device traces).

## Out of scope

Fleet / multi-device; X.509 or certificate-based device auth; DPS; Container App / Docker packaging; pyproject.toml / PEP-517 packaging (requirements.txt is fine); Makefile / justfile; integration tests against IoT Hub; `customMetrics` (using `customEvents` is enough for this slice); retry logic beyond the SDK's defaults.

## Done criteria

- `python -m pytest` passes in `apps/simulator/` with all tests green.
- `python bootstrap.py` succeeds against the live IoT Hub and creates a `.env`.
- `python simulator.py` runs for ≥ 2 minutes without connection errors.
- All four post-run verifications above return the expected results.
- Spec + plan + code committed together in one commit.
